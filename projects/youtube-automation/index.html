The problem

Publishing across YouTube channels involves repeating the same steps: preparing video details, uploading the file and checking the publishing settings. The project at RedOne Media focuses on automating that workflow.

The goal is a backend workflow for video uploads and metadata management through the YouTube Data API, while keeping API quota constraints visible.

Workflow

The local Node.js web interface talks to the FastAPI backend; it does not upload videos independently. PostgreSQL stores project, publishing-job and cooldown state. A worker on the same Windows machine reads the approved source file and calls the official YouTube Data API.

  1. Prepare and review

    Choose a local video and channel profile. AI proposes metadata; the operator reviews the draft and makes the audience, visibility and scheduling decisions.

  2. Freeze the approved version

    Confirmation checks the metadata version, source SHA-256, channel assignment and publishing policy. The approved payload is frozen into a job. A queued response means the job exists, not that the upload has succeeded.

  3. Upload once, then verify

    The worker persists an encrypted resumable-session URI before sending media and uploads in chunks. It reads the same session after an interrupted response. After processing, it applies the thumbnail and approved visibility or schedule, then reads the remote video back before reporting success.

The parallel variant separately asks for approval to start a private upload while metadata is prepared. Final confirmation updates that same video rather than uploading the file again.

Quota is a state, not a blind retry

Daily quota exhaustion and short-lived throttling have different recovery paths. The API adapter inspects the provider error reason; the worker persists the resulting state instead of repeatedly submitting a new upload.

HTTP 429		Bounded exponential backoff, with a valid Retry-After respected. The worker permits up to five retries; this is separate from the daily cooldown.
HTTP 408 / 5xxTreat retryable request failures with the bounded retry path. Keep the approved snapshot and existing upload session.
youtube_upload_outcome_unknownMove to needs_reconciliation. Do not create another session or video simply because the final response was lost.

Cooldowns are stored in PostgreSQL by quota scope and API bucket: uploads, search or general. They survive restarts and prevent other jobs in the affected scope from immediately repeating the same requests. The app's per-channel daily upload limit is a separate business rule.

After the wait, the worker rechecks permission, source file, approved snapshot and session state. Another quota response extends the cooldown. An expired schedule is re-evaluated rather than silently changed into an immediate public release.

Recovery through the official API

The current refactor uses the official Data API for automated YouTube operations. It does not drive YouTube Studio or switch to browser automation when quota runs out. The recovery path is persisted waiting, retry or reconciliation of the existing job.

Browser automation of YouTube Studio is outside the scope of this implementation.

Limitations & next steps

  • The backend and worker share local files; source content must remain unchanged. SHA-256 checks detect changes, but there is no immutable file snapshot.
  • An unknown upload result requires reconciliation. The current implementation has no manual UI/API for attaching a discovered remote video to that job.
  • A quota increase granted before the stored resume time is not automatically detected through Cloud Quotas. Waiting until the recorded retry time is the current behavior.
  • Extend live validation beyond the documented private-upload path and capture a short demo using a dedicated test channel and fictitious metadata.
