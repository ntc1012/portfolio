The problem

An employee record and a directory account represent the same person in different systems. Creating and disabling accounts manually makes it easy for those records to drift apart.

This project brings employee management and directory synchronization into one interface. The focus is the account lifecycle and visibility into administrative actions.

Architecture

The implementation has two main Python modules: Flask routes in app.py and a synchronous LDAP synchronization routine in sync_hr_ad.py. MySQL stores employee and administrator records; the application writes timestamped audit events to a local file.

HR-to-AD synchronization

  1. Read an HR snapshot

    The operator starts a sync from Flask. The module reads Employees from MySQL; the current implementation processes all records rather than consuming change events.

  2. Map employee identity

    The email prefix becomes sAMAccountName. Full name and department determine the distinguished name and target OU. The directory layout and department OUs must already match that mapping.

  3. Create or disable

    Active records invoke an LDAP add. Existing entries are skipped. Inactive records are looked up and disabled using userAccountControl; missing or already-disabled entries are skipped.

  4. Record outcomes

    LDAP outcomes are logged and per-record exceptions do not stop later records. This is account provisioning and deactivation; AD group membership and full permission reconciliation are not implemented in the reviewed sync routine.

Authentication & audit decisions

What TOTP adds

A correct password only creates a temporary login state. The administrator session becomes authenticated after PyOTP verifies an authenticator code. First-time enrollment uses a QR code, and the shared secret is saved after successful verification. This adds a second factor without an SMS delivery service.

The tradeoff is managing a shared secret and time-based verification. The reviewed code uses TOTP.verify but does not persist the last accepted time step or separately throttle failed TOTP attempts. Replay protection and second-factor rate limiting are concrete next steps.

What the audit trail records

The logger adds a timestamp and severity. The audit helper records username, source IP, action, detail and status. Events cover password and TOTP login outcomes, logout, employee creation/status changes/deletion, sync start/completion/failure, and audit/report views.

USER=demo-admin | IP=192.0.2.10 | ACTION=SYNC_AD
DETAIL=Start HR-to-AD sync | STATUS=SUCCESS

Format example with fictitious values, not captured runtime evidence. Detailed employee fields in log messages also need access and retention controls.

    Limitations & next steps

    • Sync completion is not proof that every LDAP operation succeeded. Some helpers log an LDAP failure without raising; the outer route can still report completion. Return structured per-account results and a true partial-failure summary.
    • Existing accounts are skipped rather than reconciled. Reactivation, renamed employees, OU moves and group membership need explicit handling.
    • The disable operation replaces userAccountControl with a fixed value. A follow-up should preserve unrelated flags and change only the account-disabled bit.
    • MySQL and LDAP operations are separate. Add reconciliation tests for partial failures and repeated sync runs rather than assuming a cross-system transaction.
    • Harden TOTP enrollment, shared-secret storage, reused-code rejection and attempt limits; define log access and retention before a production deployment.
